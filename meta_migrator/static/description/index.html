Key Architectural Highlights

Top-Down Step Execution

Migrate in explicit sequential steps controlled by drag-and-drop handles. No rigid hard-coded order; customize step dependencies as needed.

Dry-Run Safety Gate

The Test button runs a read-only comparison across instances using a virtual registry. Target databases remain 100% untouched.

8 Specialized Diff Widgets

Tailored OWL 2 viewers for models, fields, views, actions, and security records. Features inline word diffs, XML outlines, and risk banners.

Multi-Pass Relational Blocks

Contiguous field steps are collapsed into an atomic block executing across 3 passes, eliminating circular M2O, O2M, and compute dependency deadlocks.

Non-Destructive View Merging

When updating existing views, elements are appended into <data> without wiping target customizations.

Synchronized Verification

Clicking Test after a migration automatically computes is_in_sync, confirming complete parity with zero line deltas.

Step 1: Setting Up Remote Endpoints (Connections)

Declare the source and target Odoo instances under Meta Migrator > Connections:

Field Label Technical Key Description & Best Practices
Server URL url Base HTTP/HTTPS URL of the remote instance (e.g. https://staging.internal:8069).
Database Name db PostgreSQL database name of the target Odoo environment.
Login Username username Administrative Odoo user login with system management privileges.
API Key / Password password Remote password or Odoo User API Key (strongly recommended for security).
Timeout timeout RPC socket timeout in seconds (default: 60s).

Click Test Connection to verify credentials. A green alert box will confirm successful authentication with user ID and accessible model counts.

Step 2: Defining Migration Jobs & Step Sequences

Under Meta Migrator > Jobs, create a new job to establish a reusable migration blueprint.

Job Configuration Options

  • On Conflict: overwrite (Update if target entity exists) or skip (Preserve target entity as-is).
  • Stop On Error: Halts execution immediately if any step fails, preventing corrupted schema states.
  • Run In Background: Dispatches the job to an asynchronous ir.cron queue for large transfers.

Step Object Types

Object Type Action Inputs Execution Logic
model create model_name, target_model_name Creates custom model. If it already exists, marked as unchanged.
field create model_name, field_name Transfers fields with full attributes (relations, selections, compute logic).
view create model_name, view_type Creates primary view matching source active view of lowest priority.
view update xml_id Appends new XML nodes into existing target view <data> without overwriting customizations.
server_action create / update xml_id Synchronizes Python code, model bindings, and security action states.
menu create model_name Transfers window actions, root menus, and sub-menu hierarchies.
access_right create model_name Replicates ir.model.access CRUD permissions, auto-mapping security groups.
record_rule create model_name Transfers domain force record rules and evaluation contexts.

Step 3: Accelerating Setup with Field Generation Wizard

Click Generate field steps in the job header. Pick any model from the source instance: the wizard automatically discovers all manual custom fields and presents an interactive checklist. Select the desired fields and click Add Steps to append them to the job in 1 click!

Click Sort by dependency to automatically arrange models before fields and parents before children.

Figure 3.1: Generate Field Steps Wizard – Batch extraction of custom model fields.
4

Step 4: Dry-Run Testing & Specialized Diff Inspection

Click the Test button to perform an automated dry-run. Meta Migrator evaluates differences against the target server in pure read-only mode, generating granular change records viewable in the Runs tab.

8 Specialized OWL 2 Diff Widgets: Instead of raw JSON dumps, Meta Migrator renders dedicated interactive viewers: meta_model_create (child fields table with search/filters), meta_field_update (property diff table with risk warnings), meta_view_update (element card additions), meta_server_action (code comparison), and more.
Figure 4.1: Specialized Field Update Widget – Property comparison with high-risk warning alerts.
5

Step 5: Executing Live Migration & Sync Verification

Once diffs are audited, click Run in the job header. Confirm the safety dialog to execute the sequence against the target instance via XML-RPC.

100% In-Sync Verification: Click Test again after a completed run. Meta Migrator queries the target instance fresh: if all objects match, the run reports is_in_sync: True with +0 / -0 diff delta!
Figure 5.1: Synchronized Run State – 100% In-Sync confirmation with zero line diffs.
