# Advanced Dynamic Approval

Dynamic approval workflow builder with visual stage hierarchy and Python conditional routing for **Odoo 19**. Extends the standard `approvals` module with a fully custom stage-based approval engine that **replaces the default Odoo approval execution flow**.

---

## Overview

`Advanced Dynamic Approval` lets you design complex multi-stage approval processes using a **visual hierarchy view** (powered by `web_hierarchy`). Instead of relying on Odoo's built-in approval execution, this module introduces its **own stage-based workflow engine** where:

- A **one-to-one relationship** exists between an *Approval Category* and a *Workflow Configuration* (a category can only be bound to a single workflow).
- Each workflow is a **tree of stages** with parent/child relationships, traversed top-down.
- Each stage defines **who can approve** (a specific user **or** a user group) and an **optional Python condition** that determines whether the stage is eligible.
- A **Server Action** is automatically generated so that approval requests can be launched directly from the records of any target model.

## Key Features

- **Stage-based workflow engine** — completely custom approval flow built around a hierarchy of stages (independent of Odoo core approval stages).
- **Visual workflow builder** — stages are designed with the `web_hierarchy` view: drag-and-drop nesting, reorderable sequence, and inline previews of approver type, user/group, and condition.
- **Python conditional routing** — each stage can carry a Python expression (`result = self.field > value`). The engine evaluates conditions dynamically.
- **Approver flexibility** — a stage can be assigned to either a **specific user** or an **entire user group**, and approval can be performed by any member of the resolved approvers.
- **Automatic interface generation** — one click generates a dedicated **menu**, **list view**, **form view**, and **window action** for the approval category.
- **Generated approval form** — a dedicated form with status bar, header buttons (Send for Approval / Approve / Reject / Cancel), and an embedded **Approval History** page.
- **Approval history tracking** — every state transition is recorded (`new → pending → approved/refused/cancel`) with timestamps, approver, and eligible approvers.
- **Activity notifications** — approvers receive a `mail` activity when a request reaches their stage.
- **Initialization code editor** — a built-in Python code editor (Code tab) lets you customize how an approval request is created (pre-fill fields, set defaults, etc.) directly from the workflow configuration form.

## How It Works

### 1. Workflow Configuration (`approval.workflow.config`)

A workflow configuration binds an **Approval Category** to a **Target Model** and owns a set of **Workflow Stages**. It also holds:

| Field | Description |
|---|---|
| `name` | Human-readable workflow name. |
| `category_id` | The Odoo approval category this workflow is attached to. (One workflow per category.) |
| `model_id` | The Odoo model whose records will trigger approval requests (e.g. `sale.order`, `purchase.order`). |
| `technical_name` | Prefix used to name generated views, actions, and menus (`approval_<technical_name>_form`, etc.). |
| `state` | `draft` (editable) or `locked` (active — fields become read-only). |
| `init_code` | Python code executed by the generated server action to initialize the `approval.request` from a source record. |
| `server_id` / `action_id` / `menu_id` / `list_view_id` / `form_view_id` | References to the objects generated by `Generate Views`. |
| `stage_ids` | The tree of stages belonging to this workflow. |

**Buttons:**

- **Generate Views** — creates the form, list, action, and menu (only visible while none of them exist yet).
- **Create Server Action** — creates an `ir.actions.server` on the target model (see below).
- **Stages** — opens the hierarchy of stages for this workflow.
- **Server Action** — opens the generated server action record for inspection/editing.

### 2. Workflow Stages (`approval.workflow.stage`)

Stages form a **directed tree** (`parent_id` / `child_ids`) inside a workflow. Each stage has:

| Field | Description |
|---|---|
| `name` | Stage name. |
| `sequence` | Ordering within the same parent/level. |
| `approver_type` | `user` (specific user) **or** `group` (user group). |
| `user_id` | Approving user (when `approver_type == user`). |
| `group_id` | Approving group (when `approver_type == group`). |
| `condition_python` | Optional Python code evaluated with `self` = the approval request record. **Must assign `result`**. |
| `parent_id` / `child_ids` | Parent/child relationship for the hierarchy. |

#### Conditional routing & "first match" rule

When the workflow engine resolves the next stage(s) from a given node, it:

1. Fetches the **direct child stages** (or root stages) ordered by `sequence`.
2. Iterates through them and evaluates each stage's `condition_python` (with `self` = the approval request).
3. **As soon as a stage evaluates to `True`** — including a stage that has **no condition set** (which always returns `True`) — it is selected and the loop **stops**.

> **Rule:** If two sibling stages in the same level both return `True`, **only the first one** (highest priority / lowest sequence) is taken. This applies whether or not a condition is defined — an empty condition always returns `True`, so it acts as the "else / default" branch. Place your catch-all stage **last** (highest sequence) so that specific conditions are evaluated first.

This logic lives in `ApprovalWorkflowStage`:
- `evaluate_condition(record)` — runs the Python condition, returns `bool`.
- `get_next_stages(record)` — returns the first matching child stage (breaks on first match).
- `get_root_stages(workflow_id, record)` — returns the first matching root stage (breaks on first match).

### 3. Approval Request (custom flow)

The module **inherits** `approval.request` and adds a completely independent status field:

| Field | Description |
|---|---|
| `workflow_id` | The workflow configuration driving this request. |
| `current_stage_id` | The stage currently being processed. |
| `custom_request_status` | `new → pending → approved / refused / cancel`. Replaces reliance on Odoo core status for the custom flow. |
| `can_click_approval` | Computed flag: `true` only when the current user is one of the **eligible approvers** of `current_stage_id`. |
| `approval_history_ids` | One2many to `approval.history`. |

**Action buttons (in the generated form header):**

- **Send for Approval** — initializes the workflow: resolves the first root stage (by condition), sets status to `pending`, notifies approvers, and creates a history record. Visible only when `custom_request_status == 'new'`.
- **Approve** — resolves the next stage by condition. If a next stage exists, it becomes `pending` (approvers notified). If no next stage, the request is marked `approved`. Visible only to eligible approvers of the current stage.
- **Reject** / **Cancel** — open a reason wizard. Visible only to eligible approvers (Reject) / anytime except `cancel` and `approved` (Cancel).

### 4. Server Action & Target Model Integration

Clicking **Create Server Action** on a workflow configuration (in its form view) does the following:

- Creates an `ir.actions.server` record whose **model is the workflow's `model_id`** (the target model configured in the form view — e.g. `sale.order`).
- The server action's **Code** is the workflow's `init_code` (which the user can edit in the Code tab).
- The server action is registered via `create_action()` so it appears in the **Actions** menu of the target model's form view (e.g. *Actions → [My Workflow] Send Approval*).
- Running it from a **source record** creates an `approval.request`, initializes it by executing `init_code`, reads the generated **action/form view**, sets it as the only form view, and opens the record — all **from the view of the source model**.

> Result: from any record of the target model (e.g. a Sales Order), the user triggers the server action and a fully configured approval request is created and opened using the workflow's generated form.

### 5. Initialization Code (`init_code`) — Code Tab

The **Code** tab of the workflow configuration holds the Python executed by the generated server action **when creating an approval request from a source record**.

- The default code contains a `src_id` variable that must be set to the **current workflow configuration's ID**:

```python
# Begin: Do not remove
src_id = 1  # Replace with the actual approval.workflow.config ID
config_id = env['approval.workflow.config'].sudo().browse(src_id)
# ...creates the approval.request using config_id...
# End: Do not remove
```

> **You must update `src_id`** (in the marked section) to match the ID of the workflow configuration you are editing. Only the **Code tab** needs editing — the rest of the server-action plumbing (view resolution, action return) is handled automatically by the protected blocks (`Begin: Do not remove` / `End: Do not remove`). The server action code is synchronized to `init_code` via the `init_code` → `server_id.code` onchange.

### 6. Approval History (`approval.history`)

Every transition creates an `approval.history` record with:

| Field | Description |
|---|---|
| `request_id` | Related approval request. |
| `stage_id` | Stage at the time of the record. |
| `status` | `new / pending / approved / refused / cancel`. |
| `approver_id` | User who acted (for approved/refused/cancel). |
| `eligible_approvers_ids` | Users who could act (for pending). |
| `sent_time` / `approval_time` | Timestamps. |
| `comments` | Optional notes. |

Each created history record also posts a message to the approval request's chatter.

### 7. Approver Selection / Proxy Signing

A stage's approvers are resolved by `get_approvers()`:

- `approver_type == "user"` → the single configured `user_id`.
- `approver_type == "group"` → all members of `group_id` (`group_id.user_ids`).

This means **any group member can approve** the stage — effectively allowing **proxy / delegated signing**. Additionally, because approvers can be configured by group, you can grant whole teams the ability to sign without reconfiguring the workflow.

> Tip: to allow a flexible "sign on behalf of" at approval time, assign the stage to a **group** containing the relevant users, or configure a **user** and rely on Odoo's own *Suggested Users* widget if you extend the form further.

## Configuration Guide

### A. Create a workflow

1. Go to **Approvals → Configuration → Approval Categories** (core) and create/assign a category.
2. Go to **Approvals → Workflow → Workflow Config** and create a new config:
   - Set **Name**, **Approval Category** (one per category — enforced by constraint), and **Target Model**.
   - Set a **Technical Name** (alphanumeric + underscore only; used as a prefix for generated views/menus).
3. Click **Generate Views** to create the menu, action, form, and list view.
4. Click **Create Server Action** to create the server action on the target model.
5. Open the **Code** tab and **set `src_id`** to this workflow config's ID, then add any custom initialization logic in the user-code section.

### B. Define stages

1. On the workflow config, click **Stages** → **Create**.
2. Build the stage tree: set **Parent Stage** to nest stages, use **Sequence** to order siblings, choose **Approver Type** (user or group), and optionally write a **Python Condition** (`result = self.amount_total > 10000`).
   - Use the **Hierarchy** view to visually drag-and-drop stages.
3. Remember the **first-match rule**: place your most specific conditions first and any "else" branch (no condition) last.

### C. Use it

1. Open a record of the **Target Model** (e.g. a Sales Order).
2. From the **Actions** menu, run **[Workflow] Send Approval**.
3. The approval request is created, opened in the generated form, and routed through stages automatically.

## Important Notes & Warnings

### Do NOT uninstall if records exist
> Once the module has been **installed and has existing records** (approval requests, workflows, histories), **do not uninstall it**. Uninstalling deletes all module data and generated objects, which **corrupts / loses existing approval data** and can leave dangling references on target-model records. The maintainer provides **no support** for data recovery after uninstall in that case.
>
> Instead of uninstalling, **archive** the workflow configuration (set `active = False`) or **lock/unlock** as needed.

### Editing views and fields
You can customize the generated approval form directly:
- **Extend via code** — inherit the generated form view (`approval.<technical_name>_form`) in an XML file and add or modify fields.
- **Use Odoo Studio** (recommended) — Studio can safely add fields to `approval.request` and edit the generated form. Changes made in Studio are preserved as they target the underlying model/views.
- When adding fields, make sure they are reflected on `approval.request` so they are available to `init_code` (where `record` is a field on the server-action context that you can map to the approval request).

### Dependencies
- `base`, `approvals` (Odoo core), `web_hierarchy`.
- The module relies on `approvals` for the `approval.category` and `approval.request` base models; it does **not** use the core approval *execution* — all transitions are handled by the custom stage engine above.

## Troubleshooting

| Problem | Solution |
|---|---|
| "Create Server Action" button is missing | It appears only when `server_id` is not yet set. Click it once to generate the action. |
| Source record does not open the approval form | Make sure `src_id` in `init_code` is set to the correct workflow config ID, and that **Generate Views** was run first. |
| A stage condition is not being evaluated | Conditions must assign `result` (e.g. `result = self.amount_total > 10000`). `self` is the `approval.request` record. |
| Multiple stages match but the wrong one is taken | Remember the **first-match** rule: reorder `sequence` so the desired stage comes first, or make conditions mutually exclusive. |
| Approver cannot see the Approve button | `can_click_approval` must be `true`: the user must be in `current_stage_id.get_approvers()` **and** status must be `pending`. |
| Want to change the workflow after it is locked | Archive the config (`active = False`) and create a new one; or unlock by setting `state = draft` (manager access). |
